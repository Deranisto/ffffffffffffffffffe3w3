# APEX MAX API VISIBILITY TESTER

Read-only диагностика MAX Bot API: проверяет, видит ли один бот обычные посты
двух каналов и публикации рекламной интеграции Яндекс РСЯ. Панель — тёмная,
в стиле APEX. Тестер **только читает**: отправок сообщений и изменений каналов нет.

> ⚠️ Ключевое ограничение платформы (проверено по https://dev.max.ru/docs-api):
> в объекте `Update` 19 типов событий — рекламных среди них **нет**;
> объект `Message` содержит `sender/recipient/timestamp/link/body/stat/url` —
> флага источника **нет**. Поэтому «автоматическое обнаружение РСЯ» невозможно:
> тестер показывает только то, что реально отдал API, а происхождение каждого
> поста помечает «Источник рекламы не подтверждён» / «ВОЗМОЖНО РЕКЛАМА —
> ИСТОЧНИК НЕ ПОДТВЕРЖДЁН» (при совпадении с вашей подсказкой, что тоже не доказательство).

## Что проверяется (только документированные методы)

| Проверка | Метод | Что означает результат |
|---|---|---|
| Авторизация | `GET /me` | Успех = токен принят; Нет доступа = 401 |
| Информация о канале | `GET /chats/{chatId}` | тип/статус/название/участники |
| Права бота | `GET /chats/{chatId}/members/me` | `is_admin`, `is_owner`, `permissions` |
| История | `GET /messages?chat_id=&count=` | работает, только если бот — администратор; успех метода ≠ доступность РСЯ |
| Реальное время | `GET /updates` (короткий опрос) | достижимость потока; получение конкретных постов — только мониторингом |
| Посты интеграции Яндекса | — | **Не поддерживается**: метода/события/поля нет в API |
| Содержимое РСЯ | — | **Не поддерживается** до первого реально полученного поста |
| Поля постов | — | список полей, реально наблюдаемых в ответах |

Статусы: **Успех** (подтверждено ответом), **Не поддерживается** (нет в API),
**Нет доступа** (401/403/404), **Не удалось проверить** (сеть/таймаут — повторить).

## Развёртывание: GitHub → Railway (без локального запуска)

1. Создайте репозиторий на GitHub (например `apex-max-visibility-tester`).
2. Загрузите в него содержимое папки `apex-visibility-tester` так, чтобы
   `package.json`, `Dockerfile`, `src/`, `public/` лежали в корне репозитория.
   Вариант через веб-интерфейс: Add file → Upload files. Вариант через git:
   ```bash
   git init && git add -A && git commit -m "apex visibility tester" \
     && git branch -M main && git remote add origin https://github.com/ВАШ_ЛОГИН/apex-max-visibility-tester.git \
     && git push -u origin main
   ```
   (Это выполняется на любом компьютере с git — либо сразу храните проект в GitHub.)
3. Railway → New Project → Deploy from GitHub repo → выберите репозиторий.
   Railway сам найдёт `Dockerfile` и соберёт образ.
4. Railway → Variables, добавьте:
   - `MAX_BOT_TOKEN` = токен бота (секрет, в код не вписывать);
   - `DIAG_KEY` = длинная случайная строка (ваш ключ к панели);
   - (необязательно) `DATA_PATH=/app/data/monitor.json` + Volume, примонтированный в `/app/data`, чтобы журнал мониторинга переживал перезапуски.
5. Railway → Settings → Networking → Generate Domain. Откройте выданный URL —
   это ваша облачная панель.

## Переменные окружения

| Переменная | Обязательна | Назначение |
|---|---|---|
| `MAX_BOT_TOKEN` | да | токен бота; только сервер, в браузер не уходит |
| `DIAG_KEY` | да | ключ к `/api/check`, `/api/monitor/*` (заголовок `x-diag-key`) |
| `PORT` | нет (Railway задаёт сам) | порт панели |
| `DATA_PATH` | нет (`data/monitor.json`) | файл состояния мониторинга |
| `POLL_TIMEOUT` | нет (`30`) | таймаут Long Polling, сек (0–90) |

## Как проверить два канала

1. Откройте панель по Railway-домену.
2. Введите `DIAG_KEY`, `ID канала №1`, `ID канала №2`.
3. «Проверить API» — карточки по каждому каналу + журнал + время проверки.
4. «Начать мониторинг» — сервер начнёт опрос `GET /updates` для обоих каналов
   независимо; события и посты появятся в журнале с метками времени.
   Необязательная подсказка-маркер подсвечивает совпавшие посты как
   «ВОЗМОЖНО РЕКЛАМА», источник при этом всё равно не подтверждён.
5. Дождитесь реальной публикации РСЯ в каналах и сравните: появился ли пост
   в мониторинге. Только это — экспериментальный ответ на главный вопрос.

## Что возможно, а что требует ожидания

- Возможно сразу: авторизация, инфо о канале, права бота, история (если бот админ),
  достижимость потока событий, список реально наблюдаемых полей.
- Требует ожидания реального события: факт доставки обычных новых постов;
  факт доставки постов РСЯ; любое утверждение об их содержимом/источнике.
- Невозможно в принципе через текущий API: отдельное событие или поле
  «это реклама РСЯ»; чтение истории задним числом, если метод её не отдал;
  события, произошедшие до запуска мониторинга.

## Структура

```
package.json  tsconfig.json  Dockerfile  env.example  gitignore.txt  README.md
src/
  index.ts    — запуск, проверка конфигурации, восстановление мониторинга
  server.ts   — HTTP + статика панели + /api/* (защита DIAG_KEY)
  max.ts      — клиент документированных read-only методов MAX Bot API
  checks.ts   — диагностика со статусами (без выдумок)
  monitor.ts  — наблюдение Long Polling, вердикты источника, JSON-хранилище
public/
  index.html  app.js  styles.css  — тёмная APEX-панель (токена нет, без localStorage)
```

Локальный запуск (для проверки перед деплоем): `npm install && npm run build && npm start`
с заполненным `.env` (скопировать из `env.example`).
